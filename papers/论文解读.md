# 论文解读

读论文，搞清楚动机是什么（是为了解决什么问题/此时处在什么背景之下/是否当时的手段仍不够健全）
是怎么解决的（是否有改进的空间？后来者有没有对目前的baseline paper做出改进？）



## 动机

**论文 DODUO 的核心动机是：表格缺少语义元信息，而已有方法要么依赖人工特征/外部知识库/表头元数据，要么不能充分利用表内上下文；DODUO 用预训练语言模型 + 整表序列化 + 多任务学习，同时做列类型预测和列关系预测。** 

DODUO 主要关注两个任务：

1. **Column Type Prediction / CTA**
   预测每一列的语义类型。
   例如某列是 `person`、`city`、`birth_date`、`population`。
2. **Column Relation Prediction / CPA**
   预测两列之间的语义关系。
   例如 `person` 列和 `location` 列之间可能是 `place_of_birth`。

简而言之，动机拆成三层：

1. 如何只依靠表格自身内容，自动推断列类型和列间关系？
2. 表格语义理解需要同时利用 intra-column context 和 inter-column context。
3. Column Type Prediction 和 Column Relation Prediction 不是两个完全独立任务，它们共享语义知识，应该用一个统一模型、多任务学习来做。



## 前人的努力和局限

1. Sherlock：只看单列，缺少表格上下文
2. Sato：加入表上下文，但上下文建模比较粗糙（在Sherlock基础上加入LDA topic features/CRF 结构建模列类型之间的依赖）
3. TURL：专门做表格预训练，但依赖元数据和表结构假设（DODUO设定的是只使用表格自身内容，不依赖外部知识库或元数据）



## DODUO怎么解决

把整张表序列化成一个 token 序列，用预训练 Transformer 编码，在每一列前插入 `[CLS]`，用这些 `[CLS]` 表示列，再分别接列类型预测头和列关系预测头。

1. ==整表序列化，而不是单列或单行序列化==

假设表有三列：

```
Film | Director | Country
```

DODUO 序列化成类似：

```
[CLS] Happy Feet Cars Flushed Away
[CLS] George Miller John Lasseter David Bowers
[CLS] USA USA UK France
[SEP]

```

注意关键点：

> 每一列前面都有一个 `[CLS]`。

这些 `[CLS]` 的输出 embedding 就作为对应列的表示。



2. ==用 Transformer 的 self-attention 捕捉表格上下文==

因为整张表被送入同一个 Transformer，所以：

- 同一列内部 token 可以互相 attend；
- 不同列 token 也可以互相 attend；
- 某个 `[CLS]` 可以聚合整列以及其他列的信息。

因此，DODUO 的列向量不是孤立列向量，而是：

> contextualized column representation。

也就是带上下文的列表示。



3. ==列类型预测==
4. ==列关系预测==
5. ==多任务学习==

DODUO 同时训练：

- 列类型预测头；
- 列关系预测头。

共享底层语言模型参数，只是上面接不同任务头。

论文认为这样有两个好处：

1. 列类型和列关系共享语义知识；
2. 在标注数据不足时，多任务学习能提升泛化能力。

论文实验也显示，多任务版本 DODUO 比去掉多任务的 DOSOLO 效果更好。



## 论文不足之处 后来者居上

不足之处：

1. BERT 的 512 token 限制：宽表放不下，长文本单元格放不下，多列多行需要截断，表格信息损失

2. 对数值、日期、单位、代码类数据处理不够专门：把所有cell value都当字符串处理，对一些类型处理不够好（日期；金额；经纬度；排名；编码；ISBN；百分比；电话；时间区间），某些数值类型如 `ranking`、`capacity` 效果较低。

3. 对表格结构建模仍然比较粗：没有显式建模（行对齐关系；cell 所在行列坐标；subject-object 的逐行对应关系；表头结构；主键列；单元格类型）而对于 CPA 任务，逐行对应关系其实很重要。

4. 没有利用候选关系 label 的语义：有些label本身有很强的语义，但普通 softmax 分类不会显式理解 label name 的含义。在少样本关系上，这是一个问题。因为模型只靠训练样本学某个 label 的分类边界，少样本 label 很容易学不好，更合理的应当是引入==label description==；label name embedding；prompt；natural language hypothesis；contrastive learning；retrieval；NLI-style matching。

   

后来者居上：

方向上：

1. 利用 inter-table context；
2. 利用大语言模型；
3. 更好地做 label semantic matching；
4. 解决宽表问题；
5. 适配少样本/零样本场景。

论文集大成者：

1. RECA, PVLDB 2023：用相关表增强列类型预测
2. ArcheType, VLDB 2024：用 LLM 做零样本列类型预测
3. Column Property Annotation using LLMs, ESWC 2024：直接改进 CPA
4. SOTAB Benchmark：更贴近真实 Web 表的 CTA/CPA 数据集
